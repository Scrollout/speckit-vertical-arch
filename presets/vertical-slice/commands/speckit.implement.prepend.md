## Vertical Slice Implementation Rules

These rules take precedence over any later instruction that describes work by technical layer, such as "models, services" or "core development". Where a later instruction conflicts with these rules, follow these rules.

- Build outside-in, test-first: the skeleton first, then for each slice its contract (only what it needs), its failing tests, written as the Red step says, and the minimal code that passes them, adding only the store schema changes those tests need. Never build a contract, a store schema, or a shared model ahead of the slice that needs it.
- Build one slice at a time, in the order in `tasks.md`. Finish a slice and pass its validation before starting the next one.
- A check that did not run, or found nothing to check, is a failure, never a pass. Make the project's one test command run the plan's boundary check, its contract checks, including the drift check when a context writes its contracts in a source language, and every context's tests, and exit non-zero when any of them finds a problem, is missing, or found nothing to check. It also fails when an artifact it builds holds a test file.
- Put every file in the place the plan's Project Structure gives it. Keep each slice's request, response, and view models in that slice, and its tests in the slice's `tests/` folder. A stack that requires tests beside the code and leaves them out of its build keeps them there.
- When the context writes its contracts in a source language, write each slice's part in its `contract` file, and shared parts in `contracts/` beside the version folders. Regenerate the documents from the sources, and never edit an emitted document by hand.
- Give each slice an `entry` that its program finds from the slice folder: an HTTP slice's `entry` exposes its routes, and a consumer slice's `entry` declares its queue or subscription and the event keys it handles. Never add a slice to a hand-kept list in a program. When the stack needs an explicit list, generate it from the folders, or have the test command compare it with them.
- Keep each slice's reads and writes of stored data in its own `repository` file. Its entry, request, and response may share one file until the slice grows; split them when it does. Its handler, event, and repository are each their own file. `infrastructure/` only opens the store, defines the schema, and runs transactions. When the store uses migrations, add each schema change as a new migration in its one ordered history, and name the slice it serves in its header.
- Do not create a second copy of a domain rule that already has an owner. When a second slice needs a rule held by the first, move the rule to its one owner, and update the first slice to use it.
- Change state that a rule in `domain/` guards only through that rule's owner: load the owner through the slice's `repository`, ask it to make the change, and save its state. Never write that state around the owner. One transaction changes one owner's state, together with its outbox and inbox rows.
- Convert each request into its domain types in the handler before any decision. Check a value's rule only in its type, and test each type with one valid and one invalid value at every boundary of its rule.
- Contexts interact only through their named contracts.
- Run the test command after every slice, not only at the end. A failure is fixed before the next slice starts.
- Put every value in the home the plan's Values table gives it. Read config from environment variables. Declare every limit, pattern, enum, and error code a client sees in the contract document, and have code read it or a contract test prove the match. Keep business data such as roles and policies in the store. Only internal values that no client sees and no deploy changes stay in code, each named and defined once. A client takes the version it uses from the provider's published list. Tests and contract examples may name values.
- Never read or write another context's store. Publish each event through the outbox in the same transaction as the state change, from the schema in the publisher's `contracts/[contract-name]/[version]/`. Make each consumer record its idempotency key in the inbox in the same transaction as its state change, so a duplicate delivery changes nothing. Prefix every name a frontend shares in the browser with its context's kebab-case name. Give each workflow step before the pivot that changes state its compensation, as the plan's Workflows table names it, and retry the pivot and later steps until they succeed.
- When a slice raises a question the plan does not answer, resolve it by the planning rules' research method, and add it to `research.md` Sources and the plan's Decisions. When its confidence is below 90%, add it to Open Decisions, leave the code that depends on it unwritten, and continue with the rest.
- When a check fails, decide whether the code or the check is wrong, and fix the one that is wrong. Never loosen a check, a threshold, or a report rule to make it pass. A deliberate change to a check records its reason in the plan's Slice Rule Exceptions table.
- When a test fails, fix the code. Change a test or a source it rests on only as Changing tests below says.
- Never make code detect that it runs under test or behave differently there. A test reaches other behaviour only through inputs and configuration that the code also reads outside tests.
- Keep every check's planted-violation test and clean test passing, so each check still proves it can fail. When a change moves, renames, or restructures what a check or its planted-violation tests target, such as the sources, the layout, or how targets are found, run the test command and every check's planted-violation and clean tests before committing it, or before the next slice when git is not used.
- When the vsa check is installed, this command is not finished while the review after it reports a blocking finding: fix each one, or record a justified exception in the plan's Slice Rule Exceptions table, except a VSA-014 finding, which only Changing tests below resolves. Then run the review again, passing it the previous report. Run the review at most 3 times for this command. When the third run still reports a blocking finding, stop and report the open findings with status `FAIL`.
- Give every finding a home before reporting done: fix each warning the review reports, and each case a fresh sub-agent reports as left untested, or record it as a task in `tasks.md`, in an `#### Open items` group in the phase it belongs to, or in Polish when it belongs to no single phase. To close one instead, add it there as a checked task ending `closed: <reason>`. Never leave one only in a report. An open item recorded in this run, though unchecked, blocks neither the next phase nor reporting done: list them in the report, and do them in a later run.
- Before reporting done, stop everything the run started outside the test command, such as containers, servers, and background processes.

### Changing tests

These steps carry out the constitution's Tests change through the ledger. The test ledger entry template gives the format of an entry, and the vsa check's VSA-014 says how a change is found.

- **Terms**: A test's files are every file and setting loaded or set only for testing, wherever it lives, such as test code, fixtures, test data, helpers, test doubles, and test configuration, and the parts of the test command that set how tests run and which run: their environment, flags, and selection. The checks the test command runs, with their planted-violation and clean tests, follow the failing-check rule above instead. A requirement is anything an existing test checks, in the spec, a plan row, the data model, a contract, or seed data; these are the test's sources. A requirement is settled once a test at the merge base with the default branch, or one committed in this feature, checks it, or, without git, once any existing test does.
- **Test change**: A test change is an edit to a test's files, after its baseline, that alters what an existing test requires of the code: the code it runs, its inputs, what it asserts, or whether it runs, as a skip, a removal, or leaving it out of the selection does. An edit after which every existing test runs the same code with the same inputs and asserts at least the same is not one, such as adding a test, formatting, a move or rename, an edit that follows a rename or signature change of the code, or removing a skip. A test's baseline is its files as its latest entry lists them, otherwise as at the merge base, or as first committed when this feature added it. A moved or renamed test keeps its baseline: pair a test that disappears with any test that appears in its place before counting either as removed or added.
- **Source change**: Change a source only through the step that owns it: the spec through `/speckit-specify` or `/speckit-clarify`, plan rows and the data model through `/speckit-plan` or a Decision this command adds, and a contract or seed data through the task `tasks.md` plans for it. Trace each change to a spec requirement, or to a plan Decision with its deciding source in `research.md`. Change a settled requirement, wherever it is written, only from the user's own words, quoted beside the change: a clarification answer, or, in a later feature, the user's feature description, quoted in the later spec beside the requirement that names the earlier one as superseded. A plan Decision, or a contract or seed-data task, changes only what no settled requirement covers; a planned change to settled behaviour first takes one `/speckit-clarify` question. A source change that alters what an existing test requires makes that test due.
- **Due tests**: A test is due when you believe it wrong, when a source change made it due, when the same session wrote its latest entry and no fresh sub-agent has judged that entry, or when the commit that added its latest entry breaks the record rule below. `/speckit-tasks` gives each due test a task that names it. Before reporting done, send every due test to a fresh sub-agent with the test, its sources, the changed sources, the failing output, and its entries in every feature's ledger, never with your argument, and give parallel sub-agents different scope tags.
- **Who changes a test**: When a fresh sub-agent is available, never make a test change yourself: the fresh sub-agent makes it and writes the entry. When it judges a test right, fix the code. Its verdict rests on the requirement it cites, so do not send the test again until that requirement's text changes or a later spec supersedes it. When it judges a test wrong, it rewrites the test from its sources. When the sources contradict each other, it skips the test, and you take the conflict to the user through `/speckit-clarify`. Without a fresh sub-agent, do all of this yourself, under every rule here, and say so in each entry.
- **What a change shows**: An altered or replacing test checks no less than its sources require. It passes on the current code and fails by an assertion on a targeted change to the behaviour it checks, never on a change that breaks the build. While the code does not meet it yet, it belongs to an unfinished slice's Red point or is skipped. A skip is a strict expected failure that fails once the test passes, the stack's own, such as pytest's `xfail(strict=True)`, or else one the test command provides. Its reason names its entry, and an unchecked task in `tasks.md` names the entry. A removal comes with its replacing test, or follows a source change that dropped the requirement, and the removed test stays recoverable: in history with git, or quoted in its entry without.
- **The record**: Record every Red point, verdict, and test change as an entry in the feature's `test-ledger/` folder, written by whoever made it, naming the requirement it rests on and listing the hashes of the test files it leaves and the sources it rests on. Never edit or remove an entry. With git, commit a Red point's sources before briefing its fresh sub-agent, and make each commit that adds entries change only ledger entries and the test files those entries list, at their listed hashes. A later entry by a fresh sub-agent that judges a breached entry cures it. An entry records a change and never excuses it.
- **Before adoption**: Red points, verdicts, and test changes made before the project installed a version of the preset with Changing tests need no entry, and their tests take their baseline from the merge base or their first commit. With git, that moment is the commit that adds this section to `.specify/presets/vertical-slice/commands/speckit.implement.prepend.md`, or, when `.specify/` is not tracked, the commit that installs the preset version, as recorded in the project's history. Without git, everything that exists when this section is installed counts as before adoption, and its tests have no baseline until an entry lists them.
