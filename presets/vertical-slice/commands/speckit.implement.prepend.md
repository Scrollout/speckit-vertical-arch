## Vertical Slice Implementation Rules

These rules take precedence over any later instruction that describes work by technical layer, such as "models, services" or "core development". Where a later instruction conflicts with these rules, follow these rules.

- Build outside-in, test-first: the skeleton first, then for each slice its contract (only what it needs), its failing tests, written as the Red step says, and the minimal code that passes them, adding only the store schema changes those tests need. Never build a contract, a store schema, or a shared model ahead of the slice that needs it.
- Build one slice at a time, in the order in `tasks.md`. Finish a slice and pass its validation before starting the next one.
- A check that did not run, or found nothing to check, is a failure, never a pass. Make the project's one test command run the plan's boundary check, its contract checks, including the drift check when a context writes its contracts in a source language, and every context's tests, and exit non-zero when any of them finds a problem, is missing, or found nothing to check. It also fails when an artifact it builds holds a test file.
- Put every file in the place the plan's Project Structure gives it. Keep each slice's request, response, and view models in that slice, and its tests in the slice's `tests/` folder. A stack that requires tests beside the code and leaves them out of its build keeps them there.
- When the context writes its contracts in a source language, write each slice's part in its `contract` file, and shared parts in `contracts/` beside the version folders. Regenerate the documents from the sources, and never edit an emitted document by hand.
- Give each slice an `entry` that its program finds from the slice folder: an HTTP slice's `entry` exposes its routes, and a consumer slice's `entry` declares its queue or subscription and the event keys it handles. Never add a slice to a hand-kept list in a program. When the stack needs an explicit list, generate it from the folders, or have the test command compare it with them.
- Keep each slice's reads and writes of stored data in its own `repository` file. Its entry, request, and response may share one file until the slice grows; split them when it does. Its handler, event, and repository are each their own file. `infrastructure/` only opens the store, defines the schema, and runs transactions. When the store uses migrations, add each schema change as a new migration in its one ordered history, and name the slice it serves in its header.
- Do not create a second copy of a domain rule that already has an owner. When a second slice needs a rule held by the first, move the rule to its one owner, and update the first slice to use it.
- Change state that a rule in `domain/` guards only through that rule's owner: load the owner through the slice's `repository`, ask it to make the change, and save its state. Never write that state around the owner. One transaction changes one owner's state, together with its outbox and inbox rows.
- Convert each request into its domain types in the handler before any decision. Check a value's rule only in its type, and test each type with one valid and one invalid value at every boundary of its rule.
- Contexts interact only through their named contracts.
- Run the test command after every slice, not only at the end. A failure is fixed before the next slice starts.
- Put every value in the home the plan's Values table gives it. Read config from environment variables. Declare every limit, pattern, enum, and error code a client sees in the contract document, and have code read it or a contract test prove the match. Keep business data such as roles and policies in the store. Only internal values that no client sees and no deploy changes stay in code, each named and defined once. A client takes the version it uses from the provider's published list. Tests and contract examples may name values.
- Never read or write another context's store. Publish each event through the outbox in the same transaction as the state change, from the schema in the publisher's `contracts/[contract-name]/[version]/`. Make each consumer record its idempotency key in the inbox in the same transaction as its state change, so a duplicate delivery changes nothing. Prefix every name a frontend shares in the browser with its context's kebab-case name. Give each workflow step before the pivot that changes state its compensation, as the plan's Workflows table names it, and retry the pivot and later steps until they succeed.
- When a slice raises a question the plan does not answer, resolve it by the planning rules' research method, and add it to `research.md` Sources and the plan's Decisions. When its confidence is below 90%, add it to Open Decisions, leave the code that depends on it unwritten, and continue with the rest.
- When a check fails, decide whether the code or the check is wrong, and fix the one that is wrong. Never loosen a check, a threshold, or a report rule to make it pass. A deliberate change to a check records its reason in the plan's Slice Rule Exceptions table.
- When a test fails, fix the code. Make a test change or a source change, as the constitution's Tests change through the ledger defines them, only as that principle allows. Before reporting done, send every test that principle makes due to a fresh sub-agent, as it says, giving parallel sub-agents different scope tags, and follow its verdict.
- Keep every check's planted-violation test and clean test passing, so each check still proves it can fail. When a change moves, renames, or restructures what a check or its planted-violation tests target, such as the sources, the layout, or how targets are found, run the test command and every check's planted-violation and clean tests before committing it, or before the next slice when git is not used.
- When the vsa check is installed, this command is not finished while the review after it reports a blocking finding: fix each one, or record a justified exception in the plan's Slice Rule Exceptions table, except a VSA-014 finding, which only the constitution's Tests change through the ledger resolves. Then run the review again, passing it the previous report. Run the review at most 3 times for this command. When the third run still reports a blocking finding, stop and report the open findings with status `FAIL`.
- Give every finding a home before reporting done: fix each warning the review reports, and each case a fresh sub-agent reports as left untested, or record it as a task in `tasks.md`, in an `#### Open items` group in the phase it belongs to, or in Polish when it belongs to no single phase. To close one instead, add it there as a checked task ending `closed: <reason>`. Never leave one only in a report. An open item recorded in this run, though unchecked, blocks neither the next phase nor reporting done: list them in the report, and do them in a later run.
- Before reporting done, stop everything the run started outside the test command, such as containers, servers, and background processes.
