## Vertical Slice Principles

Place this section after Core Principles and before Governance, and adapt it to the project.

These principles add to Core Principles and replace none of them. Fill the core principle slots as you would without this section, and keep any core principle the user asks to adopt. If a core principle seems to conflict with a principle here, keep both and apply the core principle at context level. For example, a library-first principle means each context is a library.

- **Context, then slice**: Code MUST be organized by bounded context and then by feature slice. Every context MUST use the Project Structure, so every file has one place. Technical-layer folders MUST NOT be the primary structure. A language or a frontend MUST NOT create a context on its own.
- **Slices own shapes**: Each slice owns its request, response, and view models and its tests.
- **Slices own their vertical**: A slice MUST own what only it declares. When a context writes its contracts in a source language, the source of what a slice provides MUST live in the slice's `contract` file, and parts that several slices share MUST live in `contracts/`, beside the version folders, which hold only the emitted documents. The emitted documents remain the contract, and the test command MUST fail when they differ from what the sources emit. A program MUST find its slices from the slice folders, never from a hand-kept list that no check compares with them. A consumer slice MUST declare its queue or subscription and the event keys it handles, and the broker or queue configuration MUST be checked against them and the `manifest`. The store schema stays in `infrastructure/`, as one ordered migration history when the store uses migrations, and each migration MUST name the slice it serves.
- **Single owner for rules**: A domain rule used by several slices MUST have one owner and MUST NOT be duplicated. When the rule guards state that several slices change, its owner MUST hold that state and its transitions, slices MUST change that state only through the owner, and one transaction MUST change only one owner's state.
- **Values that check themselves**: A domain value with its own rule MUST be a type that rejects an invalid value when it is created. Slices MUST convert request shapes into these types before any decision, and MUST NOT check the same value rule anywhere else.
- **Contracts between contexts**: Contexts MUST interact only through named shared contracts.
- **Values have one home**: Here a value is config, a credential, a fact a client sees, business data, or an internal constant, not a domain type such as an amount of money. Config, meaning what varies between deploys, MUST come from environment variables, and credentials MUST stay outside the repository. Facts a client sees, such as versions, limits, patterns, and error codes, MUST be declared in the contract document. Business data such as roles and policies MUST live in the store. Only internal values that no client sees and no deploy changes MAY stay in code, each named and defined once.
- **CQRS per context**: Each context MUST record its own decision, defaulting to separate read and write code over one store.
- **One context, one service**: A context MUST stay in one fixed folder however it deploys. When it deploys on its own, it MUST be one service with the context's name, and a service MUST NOT span contexts. Each context MUST own its store, and no other context MAY read or write it. Its `manifest` MUST record its owner, deployment, store, and the events it publishes and consumes.
- **Names say what things do**: Slices MUST be named for what they do, never for what triggers them. Events MUST be named as a noun and a past-tense verb.
- **Outside-in, test-first**: Work MUST start from a skeleton whose checks are proven to fail. Each slice MUST write only the contract it needs, then failing tests, then the minimal code, including only the store schema its tests need. No contract, schema, or shared model MAY be designed ahead of the slice that needs it.
- **Evidence before action**: Decisions MUST be found by progressive distributed disclosure and recorded with their deciding source. Work MUST act only on decisions at 90% confidence or higher; the rest stay open.
- **Checks prove they can fail**: Every check MUST find its targets from the folders, report what it examined, pass on clean code, and fail on a planted violation. Retired names MUST be guarded. A change that moves, renames, or restructures what a check or its planted-violation tests target MUST run the test command and every check's planted-violation and clean tests before it is committed, or, without git, before the next slice.
- **Fix the cause**: A failing check or test MUST be resolved by fixing whichever of the code, the check, or the test is wrong, never by weakening one that is right. Whether a test is wrong is decided only as Tests change through the ledger says.
- **Fresh review**: The author MUST NOT review its own work, or write the tests that judge it, when a fresh agent is available. A fresh agent MUST work only in its own copy of the repository, in a folder of its own, run the test command there with its own state, and MUST NOT run git or write in the real working tree, except to write the test files and ledger entries that Tests change through the ledger gives it. When git is available, its copy MUST include the default branch and the working tree's uncommitted changes, including untracked files. Its brief MUST name the feature directory. Parallel fresh agents MUST NOT share a folder.
- **Tests change through the ledger**: This principle is the one statement of how an existing test and its sources may change. Other rules point to it.
  - **Terms**: A test's files MUST be taken to be every file and setting loaded or set only for testing, wherever it lives, such as test code, fixtures, test data, helpers, test doubles, and test configuration or profiles, and the parts of the test command that set how tests run and which run: their environment, flags, and selection. The checks the test command runs, with their planted-violation and clean tests, are governed by Fix the cause, not by this principle. A test's sources are the spec, the plan rows, the data model, the contract documents, and the seed data it was written from or reads. Each feature MUST keep a `test-ledger/` folder in its directory, holding one file per entry in the format of the preset's test ledger entry template. An entry's file name MUST carry its writer's scope: the slice the writer was briefed for, or a unique tag its brief gives it, and parallel writers MUST NOT share a scope. An entry MUST NOT be edited or removed, and no command regenerates one.
  - **Code under test**: Code MUST NOT detect that it runs under test or behave differently there. A test MAY reach other behaviour only through inputs and configuration that the code also reads outside tests.
  - **What a test change is**: A test change is an edit to a test's files, after its baseline, that alters what an existing test requires of the code: the code it runs, its inputs, what it asserts, or whether it runs, as a skip, a removal, or leaving it out of the selection does. An edit after which every existing test runs the same code with the same inputs and asserts at least the same is not one, such as adding a test, formatting, a move or rename, an edit that follows a rename or signature change of the code, or removing a skip. A test's baseline is its files as its latest entry lists them, otherwise as at the merge base with the default branch, or as first committed when the feature added it. A moved or renamed test MUST keep its baseline, and a test that disappears MUST be paired with any test that appears in its place before either counts as removed or added.
  - **Source changes**: A source MUST change only through the step that owns it: the spec through `/speckit-specify` or `/speckit-clarify`, the plan rows and data model through `/speckit-plan` or a Decision that `/speckit-implement` adds, and a contract or seed data through the task that `tasks.md` plans for it. Each change MUST trace to a spec requirement, or to a plan Decision with its deciding source in `research.md`. A requirement is settled once an existing test checks it: a test at the merge base with the default branch, or one committed in this feature, or, without git, any existing test. A source change that alters what a test requires under a settled requirement MUST trace to a spec requirement changed through `/speckit-specify` or `/speckit-clarify`, or to a later feature's spec that names the settled requirement as superseded; a plan Decision, from `/speckit-plan` or `/speckit-implement`, MAY change only what no settled requirement covers. A later feature MUST name in its spec each earlier requirement it supersedes. A source change that alters what an existing test requires makes that test due, and `/speckit-tasks` MUST give each due test a task that names it: the Red-point task of the slice whose sources made it due, or a task that sends it to a fresh agent.
  - **Who changes a test**: When a fresh agent is available, only a fresh agent MAY make a test change, and it MUST write the entry. Without one, the same session MAY, under every requirement here, and its entry MUST say so. A test is due for a fresh agent when the author of the code believes it wrong, when a source change made it due, when the same session wrote its latest entry and no fresh agent has judged that entry, or when the commit that added its latest entry breaks the entry rules below. When a fresh agent is available, every due test MUST go to one before the work is reported done, with the test, its sources, the changed sources, the failing output, and its entries in every feature's ledger, never with the author's argument. A test it judges right MUST stand and the code MUST be fixed. That verdict rests on the requirement it cites, and lapses only when that requirement's text changes or a later spec supersedes it; until then the test MUST NOT be sent again. A test it judges wrong it MUST rewrite from its sources. When its sources contradict each other, it MUST skip the test, and the conflict MUST go to the user through `/speckit-clarify`.
  - **What a change must show**: An altered or replacing test MUST NOT check less than its sources require. It MUST pass on the current code and fail by an assertion on a targeted change to the behaviour it checks, never on a change that breaks the build, or, while the code does not meet it yet, MUST belong to an unfinished slice's Red point or be skipped. A skip MUST be a strict expected failure that fails once the test passes, the stack's own or else one the test command provides. Its reason MUST name its entry, and an unchecked task in `tasks.md` MUST name the entry. A removal MUST come with its replacing test, or follow a source change that dropped the requirement, and the removed test MUST stay recoverable: in history with git, quoted in its entry without.
  - **The entry**: Every Red point, verdict, and test change MUST be an entry, written by whoever made it, that names the requirement it rests on and lists the SHA-256 of each test file it leaves and each source it rests on. The hashes detect later edits, which is what makes the ledger work without git. An entry MAY judge an earlier one, as `upheld` or `reversed`. With git, a Red point's sources MUST be committed before its fresh agent is briefed, and the commit that adds an entry MUST change only ledger entries and the test files that the commit's entries list, each at its listed hash. A later entry by a fresh agent that judges a breached entry cures the breach. An entry records a change and never excuses it: each entry MUST be judged on its own change, a change that breaks this principle is a finding however it is recorded, and no exception accepts it.
- **Findings have a home**: Every review warning, and every case a fresh agent reports as left untested, MUST be fixed, or recorded as a task, or as a checked task ending `closed: <reason>`, before the work it concerns is reported done.
- **Reliable events**: A published event MUST be a versioned contract written through an outbox in the same transaction as the state change. A consumer MUST be idempotent, recording each message's key in the same transaction as its state change. A process that spans contexts MUST name its pivot, a compensation for every step before the pivot that changes state, and a timeout.
